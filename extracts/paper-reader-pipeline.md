## 核心方法论

论文速读的本质是一个 **三层管线**：

```
PDF → 文本提取 → 语义分块 → 结构化抽取 → 压缩合并
```

每一层解决一个特定的技术问题。

---

## 第一层：PDF 文本提取

### 技术选型：PyMuPDF (fitz)

| 库 | 速度 | 中文支持 | 结构保留 |
|:---|:-----|:---------|:---------|
| PyMuPDF | ⚡ 极快 | ✅ 好 | ✅ 段落级 |
| pdfplumber | 🐢 慢 | ✅ 好 | ✅ 表格级 |
| PyPDF2 | ⚡ 快 | ⚠️ 一般 | ❌ 易丢结构 |

**PyMuPDF 是我们的一级选择**，原因：
1. 用 C 写的底层，解析速度是纯 Python 的 5-10 倍
2. 对 CJK（中日韩）字符有专门的编码处理
3. `get_text("text")` 保留段落换行，便于后续分块

### 注意点
- 扫描版 PDF 需要先 OCR（本文管线不覆盖，需外挂 OCR 引擎）
- 双栏排版需要后处理重排（可用列检测算法）
- 数学公式以文本方式提取会丢失结构，建议单独处理

## 第二层：语义分块

### 为什么要分块？

LLM 上下文窗口有限（即使 GPT-4 有 128K，精度也会随长度下降），因此需要：
1. 把长文档切成 LLM 能高效处理的块
2. 每块语义自包含，不丢上下文

### 分块策略（从粗到细）

```
PDF 文本
  │
  ├─ 第一刀：按页码分（天然分隔）
  │
  ├─ 第二刀：按段落分（双换行符）
  │   └─ 段落 = 语义原子
  │
  ├─ 第三刀：长段落按句子分
  │   └─ 句子级粒度，避免超过 max_chars
  │
  └─ 第四刀：合并短段落
      └─ 保证每块 ~500-4000 字，LLM 效率最高
```

### 关键参数

| 参数 | 推荐值 | 说明 |
|:-----|:-------|:-----|
| `max_chars` | 3000-4000 | 每块最大字符数 |
| `min_chars` | ~500 | 太短的块合并到相邻块 |
| `overlap` | 10-20% | 块间重叠，保证边界不丢信息（高级版） |

### 为什么不用固定窗口滑窗？
- 可能把一段完整叙述从中切断
- 导致 LLM 看到的上下文不完整
- 语义分块（natural chunk）比固定窗口效果好 ~15-20%

## 第三层：结构化抽取

### 抽取字段

论文信息天然结构化，抽取维度：

| 维度 | 抽取难度 | 为什么重要 |
|:-----|:---------|:-----------|
| 研究问题 | ⭐⭐ | 论文存在的理由 |
| 方法 | ⭐⭐⭐ | 核心技术贡献 |
| 主要发现 | ⭐⭐ | 结论，最有价值 |
| 数据集 | ⭐ | 可复现的关键 |
| 局限性 | ⭐⭐⭐ | 最容易被忽略，最重要的批判性信息 |
| 一句话总结 | ⭐ | 快速判断是否值得精读 |

### Prompt 工程技巧

**系统指令**：
```
你是一个顶级的论文速读助手。
你的任务：从论文片段中提取关键信息，输出结构化摘要。
```

**关键技巧**：
1. 明确输出维度（限定范围防跑偏）
2. 温度设低（0.1-0.3），保证确定性
3. 允许"未提及"（避免幻觉）
4. 用例子锚定输出格式（少样本）

---

## 第四层：合并与压缩

多块摘要 → 一份完整报告：

```
块1摘要 + 块2摘要 + ... + 块N摘要
        │
        ▼
    合并Prompt
        │
        ▼
   最终结构化摘要
```

### 合并策略
1. 去重：相同的信息只保留一次（LLM 自动处理）
2. 排序：按论文逻辑顺序重排（问题→方法→实验→结论）
3. 压缩：合并后的内容控制在 ~1500 tokens 以内

## 总结

论文速读器的技术本质不复杂：
> **PDF 解析 + 语义分块 + LLM 结构化抽取 + 压缩合并**

核心难度不在算法，而在工程细节：
- 分块粒度怎么最优？
- 抽取维度怎么设计？
- 合并时怎么去重和排序？

这些细节决定了从"能用"到"好用"的差距。
